# Lark Chat Export Skill

Safely export Feishu/Lark chat history and generate readable HTML and Markdown without modifying the raw data.

[简体中文](README.md) | **English**

## Overview

`lark-chat-export` is an AI-agent skill for safely backing up Feishu/Lark chats. It uses the official `lark-cli` to read group and one-to-one conversations visible to the authenticated user, stores raw JSON and attachments, and derives readable HTML and Markdown without modifying the raw export.

The project separates two kinds of data:

- **Raw export:** chat metadata, message JSON, and attachments returned by the official CLI. The renderer does not modify them.
- **Readable derivatives:** HTML and Markdown generated by loading the raw export. They can be deleted and regenerated at any time.

“All chats” means all conversations and retained messages accessible to the authenticated user through Feishu OpenAPI. Deleted, recalled, expired, or unauthorized records cannot be recovered.

## Features

- Enumerates visible group and P2P chats.
- Retrieves message history with automatic pagination.
- Downloads images, audio, video, and ordinary attachments.
- Preserves sender, timestamp, message type, reply relationships, and reactions.
- Generates searchable, type-filterable local HTML for every chat.
- Generates Markdown suitable for full-text search and downstream processing.
- Computes per-file SHA-256 fingerprints before and after rendering.
- Refuses to overwrite non-empty output directories.
- Does not call third-party AI summarization or image-analysis services.

## Requirements

- Python 3.10 or newer.
- The official [`lark-cli`](https://github.com/larksuite/cli).
- A configured Feishu/Lark app and an authenticated user identity.
- Read access to the target chats and their downloadable resources.

Check the CLI before exporting:

```bash
lark-cli auth status
lark-cli doctor
```

Authorize only the IM read capabilities required for export. Do not grant unrelated document deletion, permission administration, or Base write access merely for convenience.

## Quick start

### 1. Create a raw export

The output directory must be empty or absent:

```bash
python3 scripts/export_all.py \
  --cli /path/to/lark-cli \
  --output /path/to/lark-chat-export-raw
```

To export message data without attachments:

```bash
python3 scripts/export_all.py \
  --cli /path/to/lark-cli \
  --output /path/to/lark-chat-export-raw \
  --skip-resources
```

### 2. Create readable derivatives

Write the readable output to a separate new directory:

```bash
python3 scripts/render_readable.py \
  --source /path/to/lark-chat-export-raw \
  --output /path/to/lark-chat-export-readable
```

Then open:

```text
/path/to/lark-chat-export-readable/index.html
```

HTML supports local search and message-type filtering. Markdown is stored under `markdown/` for tools such as `rg`, local indexing, or later analysis.

## Output structure

Raw export example:

```text
lark-chat-export-raw/
├── manifest.json
├── chats.json
├── index.html
└── 001_example_<chat-id-suffix>/
    ├── chat.json
    ├── messages.json
    └── lark-im-resources/
```

Readable export example:

```text
lark-chat-export-readable/
├── index.html
├── manifest.json
├── source-integrity.json
├── html/
└── markdown/
```

Readable files reference raw attachments through relative paths instead of duplicating large binaries. Keep the raw and readable directories in their original relative locations when moving them, or rerun the renderer after relocation.

## Data safety

- `export_all.py` invokes only the supplied official `lark-cli` executable.
- `render_readable.py` reads the raw export and writes to a separate derivative directory.
- Both scripts refuse to overwrite non-empty output directories.
- Chat content is escaped in HTML, preventing member-supplied HTML or JavaScript from executing.
- Chat attachments may include executable files. The project stores them but never executes them.
- A successful delivery requires `source_unchanged: true` in `source-integrity.json`.

## `openai.yaml` and other AI platforms

`SKILL.md` and `scripts/` form the core of this project: the former describes how an agent should select and execute the workflow, while the latter contains deterministic data-processing logic.

`agents/openai.yaml` is an **optional OpenAI/Codex-specific adapter**. It supplies UI-facing metadata such as a display name, short description, and default prompt, and may also declare invocation policy or tool dependencies. It contains no export logic. Removing it does not prevent the Python scripts from running independently, although Codex-specific UI metadata will be lost.

Automatic discovery, plugin manifests, UI metadata, and permission declarations are not universal across AI products. When adapting this project to another platform:

1. Keep `SKILL.md` and `scripts/` as the single source of truth.
2. Confirm whether the target platform natively recognizes `SKILL.md`.
3. Add a thin platform-specific metadata or manifest file only when the target platform explicitly requires one.
4. Never duplicate or fork the Python business logic per platform; otherwise security fixes will diverge quickly.

**Different platforms may require different adapter files, but they should not require different copies of the skill's core logic.**
